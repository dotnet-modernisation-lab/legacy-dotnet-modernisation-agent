# Legacy .NET modernisation: how we work with you

**For clients with ageing .NET Framework applications** (Web Forms, WCF, CSLA, stored procedures, Windows services).

## The problem we solve

Most legacy estates are not migrated because nobody can say, with evidence, what is in them, what it will take and what could go wrong. We remove that uncertainty first, at low cost and low risk, before anyone commits to a migration.

## What makes this different

- **Evidence, not opinion.** The assessment reads your actual code, projects and database scripts. The same input always gives the same findings.
- **Honest about gaps.** What the analysis could not see is listed as questions for your team. Nothing is assumed to be fine.
- **Your people decide.** Choices such as the sign-in approach or the web page technology are put to you as plain questions, with why each matters. We do not make them for you.
- **Read-only.** Nothing in your code base is changed during assessment.

## The steps

Each step stands alone. You can stop after any of them with something useful in hand.

| Step | What you get | Status |
|---|---|---|
| **0. Discovery questionnaire** | Answers to what code cannot show: data migration and cutover, build and deployment, testing, compliance, budget and skills constraints | Roadmap. The questions are identified; the questionnaire is not yet written |
| **1. Estate assessment** | A fact-based inventory of the applications, their technologies, how they depend on each other and where the risk sits | Available |
| **2. Customer summary and architecture diagram** | A short plain-language document and a picture: the parts of the estate, who uses them, what they connect to, the decisions needed and what we could not see | Available. Diagram is delivered beside the document, not yet inside it |
| **3. Decision workshop** | A session with your technical and business leads to settle the open decisions, using the list produced in step 2 | Partly available. The decision list is produced; the workshop is run by people |
| **4. Migration strategy and phased plan** | A recommended order of work by part, relative effort bands, dependencies between parts and the decisions each phase waits for. Drafted with AI, checked automatically against the facts, reviewed by a person | Partly available. Works end to end; checking rules are still being tuned |
| **5. Pilot migration** | One chosen part migrated and proven side by side with the old one | Roadmap |
| **6. Full migration and verification** | The remaining parts migrated in the agreed order, with behaviour compared against the original | Roadmap |

## What step 1 and 2 produce, concretely

- The parts of your estate (websites, services, desktop programs, Windows services, data), each with a size band and a confidence level.
- Who uses each part, as far as the code shows, and an explicit "not known" where it does not.
- What the estate connects to outside itself (web services, file shares, email and so on).
- The decisions only your team can make, as plain questions.
- The main risks, and the list of things the analysis could not see.

## What we need from you to start

- Read access to the source repository (a copy is enough).
- Database scripts, if they are not already in the repository.
- About an hour with someone who knows how the applications are deployed and used.

## What we do not claim

- Effort figures are relative size bands, not quotes. They are not yet calibrated against delivered projects.
- The assessment sees what is in the repository. Live database contents, server settings and scheduled tasks outside the code need your input (step 0).
- We have run this on a synthetic sample estate. Wording and grouping will be refined on real client estates.

## Suggested opening conversation

1. "Which applications worry you most, and why?"
2. "Do you know today what would stop you moving to modern .NET?"
3. "Would a short, read-only assessment of one application help you decide?"

Start with step 1 on one application. It is the lowest-risk way to find out whether the rest is worth doing.
